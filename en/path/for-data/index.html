The Data & RAG Route

BuilderKnow the basics and start building

about 50 minutes

Where data comes from, whether it is usable, how to chunk it and how to test it. Finish with a minimum evaluable RAG corpus, not a pile of PDFs in a vector store.

Read in this order
  1. Data licensing
  2. Training data provenance
  3. Training Set, Test Set
  4. Data Contamination
  5. Chunking
  6. Hybrid retrieval
  7. Retrieval Quality Metrics
  8. How to clean data with AI
  9. How to write a dataset card
  10. How to build a RAG corpus with AI
Checkpoint
  1. Given a dataset, list at least three licence facts that must be checked
  2. Explain when fixed-length chunking and semantic chunking each fail
  3. Run 10 real questions through retrieval and record hit rate, citation accuracy and refusal rate
  4. Why must a data card state “not suitable for” scenarios?
  5. In RAG corpora, deduplication or version retention first?
  6. Should cleaning rules live in code or in the data card?
  7. When inter-annotator agreement is low, revise the guideline or replace annotators first?
  8. What is the most common leakage when splitting train and validation sets?
  9. What can synthetic data solve, and what can it not?
  10. What four items should a dataset delivery include at minimum?

Try answering before opening the reference. Revisit the relevant step above if needed. These answers highlight key ideas; you do not need to repeat the wording.

Question 1 · Reference answer

Licence type, commercial/redistribution/derivative terms, territory and term, whether personal data is included, and whether the original source is traceable.

Revisit this concept

Question 2 · Reference answer

Fixed length splits a condition in half and removes context; semantic chunking over-splits or over-merges messy documents without headings.

Revisit this concept

Question 3 · Reference answer

Hit rate: does the right document enter top-k; citation accuracy: does the answer cite the right passage; refusal rate: does it say “I don’t know” without evidence.

Revisit this concept

Question 4 · Reference answer

A data card should not only say what the data supports; it must prevent use on uncovered populations, languages, periods or tasks. Without exclusions, users assume general applicability.

Revisit this concept

Question 5 · Reference answer

Keep the authoritative version and version links first, then deduplicate; otherwise old and new clauses blend and retrieval returns stale text. Dedup must retain source and date, not just the shortest passage.

Revisit this concept

Question 6 · Reference answer

Both: code makes rules executable and reproducible; the data card explains rules, effects and unresolved items. Code alone hides what was removed; a card alone cannot reproduce it.

Revisit this concept

Question 7 · Reference answer

First check whether the guideline defines boundary cases and training was consistent, then whether annotators applied the same rubric. Replacing people repeats the ambiguity and loses the discovered edge cases.

Revisit this concept

Question 8 · Reference answer

The same user, document or near-duplicate appears across splits; time series also use the future to predict the past. Split by entity/time and run near-duplicate checks.

Revisit this concept

Question 9 · Reference answer

It can add rare scenarios, privacy-limited samples and format variants; it cannot replace the real distribution and may amplify generator bias. Label source and proportion, and validate on real data.

Revisit this concept

Question 10 · Reference answer

A data card, field descriptions and licence, split and version, and quality/known-gap record. Missing one leaves the recipient unable to judge usability or reproduce.

Revisit this concept
