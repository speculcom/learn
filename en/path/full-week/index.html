Checkpoint
  1. Given a new model's page, list the questions to ask: capability, limits, cost, licence, lock-in
  2. Decide API or local for a given job, and state the reasoning
  3. Read a benchmark table and name at least one thing it cannot say about your actual use
  4. Why build one minimal pipeline in week one instead of reading all the theory first?
  5. What should a daily review record so week two can continue?
  6. How do you know a one-week plan is overloaded?
  7. Moving from demo to delivery, what three things come first?
  8. Why not change model, data and evaluation in the same week?
  9. At the end of the week, what evidence shows you actually learned?
  10. In week two, what should you keep and what should you cut?

Try answering before opening the reference. Revisit the relevant step above if needed. These answers highlight key ideas; you do not need to repeat the wording.

Question 1 · Reference answer

Define the task and acceptance criteria, then check limits, data handling, total cost, licensing, export and migration. A leaderboard position cannot answer these questions.

Revisit this concept

Question 2 · Reference answer

For example, assess an API for occasional work without deployment expertise; assess a suitable local/private option when external data transfer is disallowed. Compare cost, quality, maintenance and hardware limits in both cases.

Revisit this concept

Question 3 · Reference answer

Check benchmark version, inputs, tools and scoring. It may omit your Chinese documents, long inputs, latency requirements or cost of failure. Add representative tasks of your own.

Revisit this concept

Question 4 · Reference answer

A minimal pipeline exposes real constraints: data, interfaces, cost, latency and acceptance. Read theory as questions arise; reading everything first spends time on chapters you may never use.

Question 5 · Reference answer

Record which hypotheses were confirmed or rejected, the exact blocker, the next step and where evidence sits. Do not just log “what I studied”; without decisions and evidence week two repeats week one.

Question 6 · Reference answer

If it demands theory, environment, evaluation, docs and launch at once, and any lacks a deliverable, it will squeeze the rest. Cut to one main pipeline and one acceptance result.

Question 7 · Reference answer

Failure handling, evaluation and observability first; then permissions and cost. A demo proves the happy path; delivery proves failure is visible, reversible and explainable.

Revisit this concept

Question 8 · Reference answer

Change all three and you cannot attribute improvement or regression. Move one variable at a time and keep the old version as a control.

Revisit this concept

Question 9 · Reference answer

You can explain decisions on an unseen case, reproduce the key result, state failure boundaries and leave inspectable artefacts. A written summary alone is not evidence.

Revisit this concept

Question 10 · Reference answer

Keep reusable data, evaluation and observability; cut demo-only code and tasks without acceptance criteria. Week two should deepen around one real constraint, not open five more topics sideways.
