The Builder's Route

BuilderKnow the basics and start building

about 60 minutes

Study interfaces, retrieval, tools, evaluation and cost in build order. This explains the pipeline; actual integration still needs version checks and validation.

Checkpoint
  1. Break down an API call's cost into its token segments
  2. Explain what chunking and embedding each determine in a retrieval pipeline
  3. Name the first two defenses to put in place when adding tool calling
  4. Why can an OpenAI-compatible API reach many models, and what still differs?
  5. Retrieval is weak: check chunking first or swap the embedding model? Give the order.
  6. What does retrieval augmentation solve, and what does it not?
  7. Who owns tool definition and who owns tool invocation?
  8. Does MCP mainly solve interface standardisation or permissions?
  9. Where is the line between workflow orchestration and agent autonomy?
  10. What three sample types should a minimum pre-launch evaluation set include?

Try answering before opening the reference. Revisit the relevant step above if needed. These answers highlight key ideas; you do not need to repeat the wording.

Question 1 · Reference answer

Input includes instructions, history, retrieved material and tool results; output is generated content. Apply the relevant rates and check cache, tool and retry charges separately. Do not assume one rate for every token.

Revisit this concept

Question 2 · Reference answer

Chunking defines retrieval units; embedding represents text as vectors. Check whether the answer-bearing chunk reaches candidates before investigating ranking and generation.

Revisit this concept

Question 3 · Reference answer

Validate tool names, arguments and authorization at execution. Treat retrieved text and tool results as untrusted data. Add approval and recovery according to the risk of writes or external effects.

Revisit this concept

Question 4 · Reference answer

It standardises request/response shapes and common fields so the base URL can change; model names, streaming details, tool-call formats, billing and rate limits still differ. Compare with the same request set before launch.

Revisit this concept

Question 5 · Reference answer

First check whether the answer-bearing chunk was split or never indexed, then inspect candidates and ranking, and only then swap the embedding model. Chunking and metadata errors will not be fixed by a new model.

Revisit this concept

Question 6 · Reference answer

It puts external material into context, easing knowledge cutoffs and missing sources; it cannot guarantee the right passage is retrieved, nor remove misreading, conflicting evidence or bad citations. Evaluate hits and citations.

Revisit this concept

Question 7 · Reference answer

The application defines tools for the model, including names, arguments and purpose; the model proposes calls, while the execution layer validates and authorises. A proposal is not permission to execute.

Revisit this concept

Question 8 · Reference answer

It mainly standardises discovery and invocation between models and tools/resources, lowering integration cost; permissions, audit and side effects remain with the execution layer and business systems. A protocol is not authorisation.

Revisit this concept

Question 9 · Reference answer

A workflow fixes steps and branches in advance, with the model generating inside nodes; an agent lets the model choose the next step and tool. Workflows are predictable and auditable; agents are flexible but need stronger guardrails and rollback.

Revisit this concept

Question 10 · Reference answer

Typical success cases, boundary/ambiguous cases, and cases that should be refused or escalated. Each needs real inputs and a rubric; success-only sets hide failure.
