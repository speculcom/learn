The Evaluation and Quality Route

Deep diveMethods, evaluation and safety review

about 40 minutes

Move from other people's scores to judgements you can re-run: what an evaluation actually measures, where it fails, and how to land it as a minimal flow you can record, re-run and hold accountable.

Checkpoint
  1. Say when a published score cannot transfer to your task
  2. Write two checks your scenario can judge automatically and three that need a person
  3. Name the minimum set of things to pin so others can reproduce an evaluation result
  4. What is benchmark saturation, and what do you do when it happens?
  5. How does data contamination affect scores, and how do you check it?
  6. For structured-output evaluation, check format or content first?
  7. In a migration evaluation, what changes and what stays fixed?
  8. What does observability record in an evaluation?
  9. Why can’t hallucination evaluation rely on automatic metrics alone?
  10. For a 20-item minimum evaluation, how do you split machine and human judging?

Try answering before opening the reference. Revisit the relevant step above if needed. These answers highlight key ideas; you do not need to repeat the wording.

Question 1 · Reference answer

Three common breaks: task distribution (public sets are long-form English QA, you judge Chinese tickets), method (they use automatic metrics, you need human fact checks), and version timing (the scored model or data changed). If any holds, write 'this score does not support that conclusion' instead of recycling their ranking.

Revisit this concept

Question 2 · Reference answer

Machines judge format and checkable facts: required fields present, cited ids real, dates and figures traceable to the given material. People judge quality: whether the conclusion is supported, whether it should have refused, tone and compliance risk. Record the ratio between the two layers, because automatic metrics alone say nothing about factual correctness.

Revisit this concept

Question 3 · Reference answer

Pin at least five: model and version identifier, prompt and system settings verbatim, sample set and its split, the method (script plus human rubric), and who judged under what rubric. Missing any one turns a re-run into a different evaluation whose gaps cannot be attributed. Also record when samples were collected, because they expire.

Revisit this concept

Question 4 · Reference answer

Most models approach the ceiling and scores no longer separate capability. Move to harder or more task-relevant samples, add process metrics and failure analysis instead of ranking decimal places.

Revisit this concept

Question 5 · Reference answer

Test items entering training inflate scores, especially public benchmarks. Check training cutoff against release dates, run exact/near-duplicate matching, and test unseen or perturbed versions; overlap is a risk signal, not proof.

Revisit this concept

Question 6 · Reference answer

First check parseability and required fields, then whether values are correct and citations real. Format failure blocks content scoring; content-only review misses downstream unusability.

Revisit this concept

Question 7 · Reference answer

Change the model/vendor and necessary interfaces; keep task samples, rubric, prompt intent and acceptance criteria. Changing both removes attribution and yields another incomparable evaluation.

Revisit this concept

Question 8 · Reference answer

Per run: model version, prompt, retrieved context, tool calls, latency, token usage and judgement. Without them scores cannot be explained or failures reproduced.

Revisit this concept

Question 9 · Reference answer

Automatic metrics can check citation existence and required fields, but whether a claim is supported or should have been refused needs a human reading context. Use them as a filter, not a final factual verdict.

Revisit this concept

Question 10 · Reference answer

Machines judge format, fields, citation ids and whether dates/amounts appear in the material; humans judge support, refusal appropriateness, tone and compliance. A workable split is 12 machine-first and 8 human-deep, recording disagreements.
