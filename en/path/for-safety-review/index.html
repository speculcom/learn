The Safety and Compliance Review Route

Deep diveMethods, evaluation and safety review

about 45 minutes

Split the pre-launch review into risk, data and obligation: how it can be misused, where the data goes, and what records you must keep. Finish with a written review that names unresolved items.

Read in this order
  1. AI Safety
  2. Prompt Injection
  3. RLHF / Alignment
  4. Refusal
  5. Output Overreach and Refusal
  6. Red Teaming
  7. Data Sovereignty
  8. Data Residency
  9. Privacy & Compliance
  10. Generative AI Compliance Duties
  11. Watermarks and Content Credentials
  12. Observability
Checkpoint
  1. Name three risk areas you would press for in a review meeting and what evidence answers each
  2. Judge whether a feature triggers a record-keeping obligation and cite which official text it comes from
  3. Write one item you cannot confirm as safe and say which official statement is missing
  4. Give one piece of evidence each for the input and output sides of prompt injection.
  5. Why can’t refusal and out-of-scope output be judged by “did it refuse” alone?
  6. What should a minimal red-team record contain?
  7. What does preference alignment solve, and what does it not?
  8. What evidence do “data never leaves the network” and “data residency” each need in review?
  9. Why is observability part of a safety review?
  10. What three elements must a “cannot confirm safety” conclusion contain?

Try answering before opening the reference. Revisit the relevant step above if needed. These answers highlight key ideas; you do not need to repeat the wording.

Question 1 · Reference answer

Take input (prompt injection, instruction override), output (refusal boundaries, out-of-scope content) and data (leaves the network, residency). For input ask how interception works and what happens after a bypass; for output ask the conditions of refusal, not whether refusal exists; for data read the retention and deletion terms verbatim. A bare 'passed security testing' claim is not evidence.

Revisit this concept

Question 2 · Reference answer

Ask whether user content enters the model, whether output is published externally, and whether inputs are retained. Services that generate or spread content usually face labelling and record duties; the scope follows the official text in force for your jurisdiction, not peer practice. If verified, write the document name and date into the review record; if not, mark it unverified instead of writing 'not applicable'.

Revisit this concept

Question 3 · Reference answer

Write it as 'not stated officially' plus which specifics are absent. If you only find marketing-level claims about guardrails but no description of interception, post-bypass handling or log retention, record that effectiveness cannot be confirmed and list the three missing items. Keeping the unknown in the conclusion is more useful than a tidy judgement that collapses during incident review.

Revisit this concept

Question 4 · Reference answer

Input evidence: a retrieved document saying “ignore previous instructions” and a log of the external request it triggered. Output evidence: a call record showing system-prompt leakage or an unauthorised tool. Both must link to the session and authorisation outcome.

Revisit this concept

Question 5 · Reference answer

A refusal can be over-cautious or missing when needed; evaluate whether the condition covers risk, whether a safe alternative is offered, and whether out-of-scope output is blocked and traceable. Refusal rate alone hides both errors.

Revisit this concept

Question 6 · Reference answer

Goal and scope, input samples, model version and settings, rubric, verbatim failures, fixes and recheck date. “Tested, no issue” cannot be reproduced.

Revisit this concept

Question 7 · Reference answer

It makes output fit human preferences and safety constraints; it does not guarantee truth, cover every cultural context or prevent over-refusal. Alignment shapes behaviour, not facts.

Revisit this concept

Question 8 · Reference answer

For no-egress, inspect network boundaries, logs and third-party calls; for residency, inspect storage region, cross-border transfer and contract terms. Both need current version and check date, not a sales claim.

Revisit this concept

Question 9 · Reference answer

Without logs you cannot prove a block worked, review privilege abuse or injection, or answer who did what when. Review that key events are recorded, searchable and retained long enough.

Revisit this concept

Question 10 · Reference answer

Which official statement is missing, how far the current evidence goes, and who must supply what by when. Make it an actionable unknown, not a vague “there is risk”.
